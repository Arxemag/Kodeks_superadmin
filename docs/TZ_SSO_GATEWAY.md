## 1. Контекст

**Что за система.** `Kodeks_superadmin` — бэкенд-прослойка между внешней платформой
ИТРХАБ и каталогом «Кодекс». Каталог — это набор сайтов `cabinet-02..07.kodeks.expert`,
у каждого клиента (идентифицируется кодом **reg**, напр. `465302`) свой хост.
Соответствие `reg → base_url` лежит в таблице `reg_services`.

**Задача.** Пользователь ИТРХАБ нажимает «перейти в кабинет» и должен попасть в свой
кабинет на `cabinet-0X.kodeks.expert` **без ввода логина и пароля**. Учётные записи
в ИТРХАБ и в каталоге совпадают по логину и паролю.

**Почему нельзя проще.** Куки домена может поставить в браузер только сам домен.
Домен фронта не может «подсунуть» браузеру куки `cabinet-03.kodeks.expert` — это
политика браузеров, обойти её нельзя. Куки, которые уже умеет отдавать наш Auth API
(`POST /api/expert/reg/{reg}`), пригодны только для сервер-серверных вызовов.
Полное обоснование — [SSO_FRONT.md, раздел 0](SSO_FRONT.md).

**Идея решения.** На домене каталога появляется единственный новый путь `/sso`.
Nginx проксирует его в наш Auth API. API логинится в каталог сервер-сайд (этот флоу
уже реализован) и отвечает браузеру `302` + `Set-Cookie`. Так как запрос пришёл на
домен каталога, куки получаются first-party и браузер их принимает. Пароль
пользователя в браузер не попадает — между фронтом и шлюзом ходят одноразовые тикеты.

```
Браузер                     Бэк фронта              Auth API (наш)         Каталог
   │  клик «в кабинет»          │                        │                    │
   │ ──────────────────────────▶│                        │                    │
   │                            │ POST /sso-ticket       │                    │
   │                            │ ──────────────────────▶│  выдал ticket      │
   │  302 на https://cabinet-03.kodeks.expert/sso?ticket=XYZ                   │
   │ ◀──────────────────────────│                        │                    │
   │  GET /sso?ticket=XYZ  ─── nginx на домене каталога ─▶│                    │
   │                            │                        │ логин под юзером   │
   │                            │                        │ ──────────────────▶│
   │                            │                        │ ◀── куки сессии ───│
   │  302 → /docs/?... + Set-Cookie (first-party)         │                    │
   │ ◀───────────────────────────────────────────────────│                    │
   │  открывает кабинет, уже авторизован                                       │
```

## 4. Исследовательская часть (выполняется первой)

Результат — файл `docs/SSO_RESEARCH.md` с ответами и подтверждениями (лог запроса,
заголовки ответа, скриншот). Пункты И-1…И-6 влияют на реализацию, поэтому идут **до** кода.

- **И-1. Минимальный набор кук.** Какие именно куки каталог ставит при успешном логине
  и какие из них обязательны для доступа к кабинету. Задача — не тащить в браузер лишнее.
- **И-2. `HttpOnly`.** Читает ли фронтенд каталога свои куки из JavaScript. Если нет —
  ставим `HttpOnly` (безопаснее). Если да — выяснить, какие именно куки должны остаться
  доступными скриптам. Проверять на живом кабинете.
- **И-3. `SameSite`.** Подтвердить, что при `SameSite=Lax` куки доезжают на первом же
  переходе после `302` (переход top-level GET — по спецификации должны, но проверить).
- **И-4. `Domain=.kodeks.expert`** (для варианта Б). Принимает ли каталог куку,
  выставленную с доменным атрибутом родительской зоны.
- **И-5. Длительность логина.** Замерить полное время `AuthService.login(reg, name)`
  на живом кабинете — это три последовательных запроса к каталогу. Нужно для выбора
  таймаута (см. требование НФ-2). Дать медиану и худший случай из ~20 прогонов.
- **И-6. Повторный вход.** Инвалидирует ли новый логин пользователя его предыдущую
  сессию. Критично: если да, второй клик «в кабинет» выбросит пользователя из первой
  вкладки, и это надо явно описать в отчёте как известное ограничение.
- **И-7. Поведение при пустом пароле.** В `service.py:215` при пустом поле `psw` на
  странице пользователя подставляется **пароль администратора**. Выяснить, при каких
  учётных записях поле пустое и что тогда происходит. Предложить решение — согласовать
  с заказчиком до реализации (см. открытый вопрос ОВ-3).

## 5. Функциональные требования

Новый модуль: `services/auth_service/sso.py` (роутер + логика), при необходимости
`services/auth_service/sso_store.py` (хранилище тикетов).

### 5.1. `POST /api/expert/sso-ticket` — выдача тикета

Вызывает **бэкенд фронта**, сервер-серверно. В браузер этот эндпоинт не попадает.

**Запрос**
```
POST /api/expert/sso-ticket
X-Api-Token: <значение SSO_API_TOKEN>
Content-Type: application/json

{
  "reg": "465302",
  "uid": "n.krapivina",
  "path": "/docs/?nd=606025000&infoboard=P000F"
}
```

- `reg` — код клиента, должен присутствовать в `reg_services`.
- `uid` — логин пользователя в каталоге.
- `path` — куда отправить пользователя после входа. Необязательный, по умолчанию `/`.

**Ответ 200**
```json
{
  "ticket": "3pJ9…",
  "url": "https://cabinet-03.kodeks.expert/sso?ticket=3pJ9…",
  "expires_in": 60
}
```

`url` собирается сервером из `base_url` для этого `reg` — фронт не конструирует
его сам. Для варианта Б (`SSO_COOKIE_DOMAIN` задан) хост в `url` — `sso.kodeks.expert`
из новой переменной `SSO_GATEWAY_URL`.

**Ошибки**

| Код HTTP | `code` | Когда |
|---|---|---|
| 401 | `SSO_TOKEN_INVALID` | нет или неверный `X-Api-Token` |
| 404 | `REG_NOT_FOUND` | `reg` отсутствует в `reg_services` |
| 400 | `SSO_PATH_INVALID` | `path` не прошёл валидацию (см. ФТ-3) |
| 422 | `VALIDATION_ERROR` | не хватает полей (стандартный обработчик) |

### 5.2. `GET /api/expert/sso?ticket=...` — вход

Сюда приходит **браузер пользователя** через nginx на домене каталога.

**Требование ФТ-1 (ключевое): единственный параметр — `ticket`.**
`path`, `reg` и `uid` берутся из тикета, а не из query. Это устраняет целый класс
атак: подменить цель редиректа через URL невозможно в принципе.

> Примечание: в комментариях к nginx-конфигам показан вариант с `&path=` в URL —
> он устарел, сами блоки `location = /sso` менять не нужно (они пробрасывают
> `$is_args$args` целиком). Комментарии поправить в рамках этой задачи.

**Порядок обработки**
1. Достать и **сразу удалить** тикет из хранилища (атомарно, до логина) — гарантия
   одноразовости даже при двух параллельных запросах.
2. Тикет не найден / просрочен / уже использован → `401 SSO_TICKET_INVALID`.
3. Сверить хост (требование ФТ-2).
4. `AuthService.login(reg=ticket.reg, name=ticket.uid)`.
5. Ответ `302 Location: {ticket.path}` + `Set-Cookie` на каждую куку (требование ФТ-4).

**Требование ФТ-2: сверка хоста.** Заголовок `Host` (вариант А) должен совпадать
с `base_url` для `reg` из тикета. В варианте Б, где `Host` — это шлюз, сверяется
целевой хост из тикета. Не совпало → `400 SSO_HOST_MISMATCH`. Без этой проверки
чужой домен, проксирующий на наш API, получает вход в любой кабинет.

**Требование ФТ-3: валидация `path`** (на выдаче тикета, п. 5.1):
- начинается ровно с одного `/`;
- не начинается с `//` (protocol-relative URL — уводит на чужой домен);
- не содержит `\` и управляющих символов;
- не содержит `:` до первого `/` (отсекает `javascript:` и подобное);
- длина ≤ 2048.

Всё, что не прошло, — `400 SSO_PATH_INVALID`. Тест на open redirect обязателен (Т-5).

**Требование ФТ-4: атрибуты кук.** `AuthService.login` возвращает `dict` вида
`{имя: значение}` (`service.py:141`) — атрибуты каталога при этом теряются. Выставляем свои:

| Атрибут | Значение |
|---|---|
| `Path` | `/` |
| `Secure` | да (только HTTPS) |
| `SameSite` | `Lax` |
| `HttpOnly` | по результату исследования И-2 |
| `Domain` | из `SSO_COOKIE_DOMAIN`; если переменная пуста — атрибут не выставляется (host-only) |
| срок | сессионная кука (без `Max-Age`/`Expires`) |

**Требование ФТ-5: ошибки для браузера.** Этот эндпоинт открывает человек, а не код.
На ошибку отдавать простую HTML-страницу («Ссылка для входа устарела, вернитесь на
портал и попробуйте снова») с корректным HTTP-статусом, а не JSON-трейс.
Технические подробности — только в лог.

### 5.3. Хранилище тикетов

- Интерфейс: `issue(reg, uid, path) -> ticket` и `pop(ticket) -> TicketData | None`
  (`pop` — атомарное «взять и удалить»).
- Реализация по умолчанию — in-memory с TTL и вытеснением просроченных.
- **Ограничение, которое надо явно задокументировать:** in-memory работает только при
  одном инстансе `auth-api` и теряется при рестарте (пользователь получит
  «ссылка устарела» и повторит клик — некритично).
- Код структурировать так, чтобы вторая реализация (таблица `sso_tickets` или Redis)
  добавлялась без правки эндпоинтов. Саму вторую реализацию сейчас **не писать** —
  см. открытый вопрос ОВ-1.
- Тикет: `secrets.token_urlsafe(32)`. Не выводимый из `reg`/`uid`/времени.

## 6. Нефункциональные требования

- **НФ-1. Секреты в логах.** Ни пароль, ни значения кук, ни тикет целиком в лог не
  попадают ни на одном уровне, включая `DEBUG`. В тикете логировать первые 6 символов.
  **Отдельно:** в существующем коде сейчас пароль и куки пишутся в DEBUG-лог
  (`service.py:213`, `service.py:220`, `service.py:263`). В рамках этой задачи —
  убрать или заменить на маскированный вывод.
- **НФ-2. Таймаут.** `AuthService.login` ограничен `AUTH_HARD_TIMEOUT`, по умолчанию
  **2.0 сек** (`common/config.py:155`), а пользовательский флоу — три запроса к каталогу.
  Для `/sso` использовать отдельный таймаут `SSO_LOGIN_TIMEOUT` (дефолт выставить
  по замерам И-5, ориентир 15 сек). Иначе штатный вход будет падать по `TIMEOUT_ERROR`.
- **НФ-3. Метрики** в `services/auth_service/metrics.py`:
  `sso_tickets_issued_total`, `sso_requests_total{result}` (`ok` / `invalid_ticket` /
  `host_mismatch` / `auth_failed` / `error`), `sso_latency_ms`.
- **НФ-4. Совместимость.** Существующие эндпоинты и 88 тестов должны продолжать
  проходить без изменений. Модуль отключаемый: при `SSO_ENABLED=false` роутер
  не подключается.
- **НФ-5. Стиль кода** — как в репозитории: `from __future__ import annotations`,
  докстринги на русском в стиле соседних модулей (что делает + как инициализируется),
  типизация, ошибки через наследников `ServiceError`, логгер через
  `common.logger.get_logger`.

## 10. Открытые вопросы (решить до или в начале работ)

- **ОВ-1. Сколько инстансов `auth-api` будет на проде?** Один → достаточно in-memory
  хранилища. Больше одного → тикеты нужно вынести в БД или Redis, это +0.5 дня.
- **ОВ-2. Вариант развёртывания — А или Б?** На код влияет только дефолтами ENV,
  но определяет, какие ручные проверки возможны на этапе сдачи.
- **ОВ-3. Пустой пароль пользователя** (см. И-7): подставлять пароль администратора,
  как сейчас, или отдавать явную ошибку? Текущее поведение для SSO означает тихий
  вход под админскими кредами.
- **ОВ-4. Логины ИТРХАБ и каталога.** Совпадение проверено только на одном клиенте.
  Если где-то расходятся, потребуется маппинг `uid ИТРХАБ → логин каталога` — это
  отдельная задача, в текущую оценку не входит.
