## 0. Развилка: какой вариант делаем

Вариант 1 не блокирует вариант 2 — можно запустить первый сейчас и мигрировать позже,
фронтовый вызов при этом меняется на одну строку (POST-форма → редирект на `/sso`).

| Условие | Вариант |
|---|---|
| Нужно «вчера», пароль в JS фронта допустим | **1** — автологин `login.asp` |
| Пароль в браузере запрещён, есть доступ к nginx каталогов | **2** |
| Пароль запрещён, серверы каталогов трогать нельзя, но зона `kodeks.expert` наша | **2б** |

**Решение принимает заказчик.** Пока оно не принято, задачи блока 2 не начинаем —
это ~2 endpoint-а, хранилище тикетов и nginx-правило на 6 кабинетах.

## 2. Вариант 2 / 2б — SSO-шлюз

### 2.1. Наш код (auth-api)

Новый модуль `services/auth_service/sso.py` (APIRouter, подключить в `create_app()`
рядом с `app.include_router(reg_admin.router)`, `services/auth_service/app.py:152`).

- [ ] **Б-3. `POST /api/expert/sso-ticket`** — для бэка фронта, не для браузера.
      Вход `{reg, uid}` → выход `{ticket, url}`, где `url` — готовая ссылка на `/sso`.
      Тикет: `secrets.token_urlsafe(32)`, TTL 60 сек, одноразовый, привязан к паре `reg+uid`.
      Закрыть заголовком `X-Api-Token` (новая переменная `SSO_API_TOKEN`) — иначе любой,
      кто дотянулся до порта 8000, выпишет себе вход в любой кабинет.
- [ ] **Б-4. `GET /api/expert/sso?ticket=...&path=...`** — сюда приходит браузер через nginx.
      Порядок: погасить тикет (до логина, чтобы гонка не дала два входа) → `AuthService.login(reg, name=uid)`
      → ответ `302 Location: {path}` + `Set-Cookie` на каждую куку из результата.
- [ ] **Б-5. Валидация `path` — защита от open redirect.** Принимать только строку,
      начинающуюся с одного `/`, без `//` в начале и без `scheme:`. Иначе — 400.
      Без этого `/sso?...&path=https://evil.tld` превращает домен каталога в редиректор.
- [ ] **Б-6. Сверка `Host`.** Хост из заголовка (вариант 2) или query-параметра `host`
      (вариант 2б) должен совпадать с `base_url` для этого `reg` из `reg_services`.
      Не совпал — 400, а не «залогинить куда просят».
- [ ] **Б-7. Атрибуты кук.** `AuthService` отдаёт `dict(client.cookies)` —
      только имя и значение, атрибуты каталога теряются
      (`services/auth_service/service.py:141`). Выставляем свои: `Path=/`, `Secure`,
      `SameSite=Lax` (обязателен — при `Strict` куки не уедут на первом переходе),
      `Domain=.kodeks.expert` **только** для варианта 2б (новая переменная `SSO_COOKIE_DOMAIN`,
      по умолчанию пусто = host-only).
      `HttpOnly` — под вопросом: проверить на живом каталоге, не читает ли он свои куки из JS.
- [ ] **Б-8. Хранилище тикетов.** In-memory dict хватит для одного инстанса auth-api.
      Если контейнеров будет больше одного (или планируется рестарт без потери входов) —
      таблица `sso_tickets` (`scripts/migrations/005_sso_tickets.sql`) или Redis.
      **Решить до реализации**, переделывать потом дороже.
- [ ] **Б-9. Таймаут.** `AUTH_HARD_TIMEOUT` по умолчанию **2.0 сек**
      (`common/config.py:155`), а пользовательский флоу — это три запроса к каталогу
      (логин админа → страница пользователя → логин пользователя). Для `/sso` нужен
      отдельный, больший таймаут, иначе штатный ответ будет `TIMEOUT_ERROR`.
- [ ] **Б-10. Логи.** Ни пароль, ни значения кук, ни тикет целиком в лог не пишем.
      Сейчас `service.py:213` и `service.py:263` логируют пароль и куки на уровне DEBUG —
      перед выкаткой SSO на прод убрать (на проде `LOG_LEVEL=INFO`, но это мина).
- [ ] **Б-11. Метрики** `sso_requests_total{result}`, `sso_latency_ms` — по образцу
      `services/auth_service/metrics.py`.
- [ ] **Б-12. Тесты** `tests/test_sso.py`: тикет одноразовый; протухший тикет → 401;
      `path` с внешним URL → 400; чужой `Host` → 400; успех → 302 + Set-Cookie.
- [ ] **Б-13.** Обновить `.env.example` и README: `SSO_API_TOKEN`, `SSO_COOKIE_DOMAIN`,
      `SSO_TICKET_TTL`, `SSO_ENABLED`.

## 3. Порядок и зависимости

```
З-1 (решение по паролю в JS)
 ├─ да ──▶ Ф-1..Ф-5 + Б-1, Б-2 ──▶ вариант 1 в проде (дни)
 └─ нет ─▶ И-1/И-2 или И-6/И-7 (инфраструктура, внешние люди — начинать первыми)
            параллельно Б-8 (решение по хранилищу) ──▶ Б-3..Б-13 ──▶ И-5/И-9 ──▶ Ф-6, Ф-7
```

Инфраструктурные пункты зависят от чужих команд и тянутся дольше кода — если идём
в вариант 2, И-1/И-2 (или И-6/И-7) запускаем в первый же день, код пишем параллельно.

Оценка нашей части (Б-3..Б-13): ~день работы. Инфраструктура — по срокам Кодекса.

## 4. Открытые вопросы

1. **Кто владеет зоной `kodeks.expert` и nginx на серверах каталогов** — от этого
   зависит выбор между 2 и 2б. Пока не ответили — обе ветки висят.
2. **Сколько инстансов auth-api будет на проде** — определяет Б-8 (память или БД).
3. **Совпадают ли логины ИТРХАБ и каталога у всех клиентов** — проверено только на 465302
   (`n.krapivina`). Если где-то расходятся, нужен маппинг `uid ИТРХАБ → логин каталога`,
   это отдельная задача и в текущей оценке её нет.
4. **Поведение при пустом пароле.** `_fetch_user_password_as_admin` при пустом поле `psw`
   подставляет пароль админа (`services/auth_service/service.py:215`). Для SSO это значит
   тихий вход под чужими кредами либо 401 — надо решить, какой из двух исходов правильный.
