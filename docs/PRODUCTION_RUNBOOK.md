# Подготовка и проверка выкладки

Документ относится к текущему этапу исправления парсеров, полной формы, подтверждения записей и обработки Kafka. Он не означает выполнение всего `TZ_PRODUCTION_READY.md`. Живой каталог проверяется с сервера после установки кандидата; до проверки worker не должен обрабатывать поток действующих компаний.

## Перед установкой

1. Зафиксировать commit кандидата и предыдущего образа. Сохранить резервную копию БД и выгрузку групп, членства, ACL, дерева кабинетов и виджетов затрагиваемого тестового каталога. Убедиться, что копии можно восстановить.
2. Остановить старый единый worker и все отдельные users/init_company/correct-cabinet воркеры. Новый и старый код не должны одновременно изменять каталог. Приостановка worker не удаляет Kafka-события; проверить срок хранения Kafka и размер накопившейся очереди.
3. Сверить имена топиков, consumer group и сохранённые offsets. Не менять группу ради выкладки и не выполнять reset offsets без отдельного плана переигрывания.
4. Проверить справочник `reg_services`: все регистрации одного реального каталога должны использовать один канонический `base_url`. Разные DNS-алиасы одного каталога нельзя автоматически распознать; они обходят блокировку по URL.
5. Для обновления выполнить `python -m scripts.init_db` без seed. Мигратор ведёт `integration_schema_migrations`: применённые имена, SHA-256 и дату. Совпадающие миграции пропускаются; изменённая уже применённая миграция или изменение целевых имён таблиц останавливают запуск. SHA-256 вычисляется по SQL после подстановки имён таблиц. При первом запуске ledger над старой схемой исходные идемпотентные миграции выполняются один раз для регистрации истории. Проверить этот переход на копии текущей БД. SQL и записи ledger выполняются одной транзакцией под общей блокировкой мигратора.
6. Сверить `.env` с `.env.example`, доступность PostgreSQL, Kafka и Chromium. `CATALOG_LOCK_TIMEOUT` ограничивает ожидание блокировки; не увеличивать concurrency без проверки пула БД и длительности запросов. Для единых HTTP/API портов использовать конфигурацию проверяемой версии Compose.

## Установка кандидата без запуска потребления

Из каталога проекта на сервере:

```bash
docker compose stop worker
docker compose build auth-api worker
docker compose run --rm --no-deps worker python -m scripts.init_db
docker compose up -d chromium auth-api
docker compose ps
```

Отдельные процессы, запущенные вне Compose, останавливаются отдельно. Текущий `deploy.yml` запускает тесты, проверяет, что проверенный commit всё ещё является вершиной `release`, и вызывает `scripts/deploy.sh`. По умолчанию скрипт оставляет worker остановленным; опция ручного workflow `start_worker` включает его только после миграции и готовности API. Выкладки сериализованы. Если ветка сменилась после тестов, старый запуск прекращается до выкладки непроверенного commit.

`catalog_user_group_ownership` хранит только подтверждённые назначения интеграции: `reg`, логин, набор ID групп и время записи. Внутренний ID пользователя предусмотрен отдельным nullable-полем. При первом обращении запись отсутствует: это означает отсутствие известного владения, а не право удалить все текущие группы пользователя. Существующие ручные назначения сохраняются. Владение фиксируется после проверки внешнего изменения; при аварии до этой записи назначение может остаться неучтённым и будет сохранено при последующих изменениях. Это консервативное поведение нужно учитывать при сверке старых данных.

Seed не нужен для обновления. `python -m scripts.init_db --seed` теперь делает upsert стандартных записей и сохраняет остальные регистрации. `--keep-existing` оставлен как устаревший совместимый флаг и не меняет поведение. Полная очистка справочника возможна только явной командой `--seed --reset-reg-services`; при обычной выкладке её не использовать. Изменять применённые SQL-файлы или вручную переписывать checksum вместо новой миграции нельзя.

Проверить HTTP API командой с фактическим портом. `/ready` проверяет обязательные таблицы и колонки; `/health` проверяет соединение с БД. Ни один из них не доказывает совместимость форм каталога или работу Kafka.

```bash
curl --fail http://127.0.0.1:8000/api/expert/ready
```

## Read-only проверка каталога

Связь отдела с ID группы имеет происхождение `created` или `adopted`. Существующая группа, найденная в каталоге, записывается как `adopted`; её переименование не выполняется автоматически. При ошибке `ADOPTED_GROUP_RENAME_REQUIRES_APPROVAL` оператор сначала проверяет ID группы, её участников и влияние переименования на другие отделы. Если переименование действительно требуется, для конкретного отдела и регистрации можно выставить `catalog_group_rename_allowed = true` в таблице `department_service_mapping` и затем повторить операцию. Это разрешение сохраняется для последующих переименований; его можно снять обратно. Для ранее связанных групп без известного происхождения действует тот же запрет до явного решения. Группы, подтверждённо созданные интеграцией, могут переименовываться с сохранением ID.

Подставить согласованный тестовый `reg` из справочника. Вызов не изменяет группы, пользователей, ACL и виджеты; выполняет логин и чтение. Отчёт содержит только названия/количество полей и коды ошибок, без значений полей.

```bash
docker compose run --rm --no-deps worker python -m scripts.catalog_preflight --reg TEST_REG --output /tmp/catalog-preflight.json
```

Для проверки существующей формы пользователя добавить `--user TEST_LOGIN`. JSON всегда выводится в stdout; файл внутри одноразового контейнера исчезнет при его удалении. Для сохранения отчёта на хосте:

```bash
docker compose run --rm --no-deps worker python -m scripts.catalog_preflight --reg TEST_REG > catalog-preflight.json
```

Exit code 0 означает, что все запрошенные контракты чтения распознаны; он не доказывает создание/сохранение. Exit code 1 означает `UNVERIFIED` хотя бы у одного шага. Не включать worker при неизвестных формах групп/пользователей.

`acl_form_get` намеренно проверяет только GET. Если ACL появляется после кнопки «Настройки сервисов» или JS, этот шаг будет `UNVERIFIED`: preflight не отправляет административный setup POST. Проверку чтения и сохранения браузерного пути нужно отдельно выполнить на тестовой компании; общий `ok=false` нельзя переименовывать в PASS без доказательства.

При несовпадении разметки сохранить отдельную диагностическую копию нужной формы для адаптации парсера. Не добавлять подстановку пустого списка групп или минимального POST вместо исправления разбора.

## Прогон записи на отдельной тестовой компании

После распознавания форм подготовить JSON-файлы с реальными ID отделов, кабинетами и отдельным тестовым пользователем. Тестовые группы и пользователя отличать от действующих данных. Не использовать случайную действующую компанию.

Запускать по одному сценарию без Kafka; файлы примеров ниже должны быть подготовлены в контейнере или подключены отдельным volume:

```bash
docker compose run --rm --no-deps worker python -m scripts.init_company_probe --payload-file /tmp/test-company.json
docker compose run --rm --no-deps worker python -m scripts.users_real_probe --topic create-user --payload-file /tmp/test-user.json
```

Обе команды выполняют реальные изменения. `init_company_probe --dry-run` тоже изменяет маппинг БД и поэтому не является read-only preflight.

Обязательная последовательность: существующая группа → повтор инициализации без нового ID → создание пользователя → повтор создания → изменение одного поля с сохранением остальных → назначение существующих групп → проверка ACL → повтор события → перезапуск во время тестовой операции → проверка восстановления/ошибки. После каждого шага сверить фактическое состояние каталога, а не только HTTP-код и лог.

Для виджетов сначала использовать `python -m scripts.cabinet_edit_probe --reg TEST_REG --board-id TEST_BOARD --list`. Существующий `--self-test` удаляет и восстанавливает виджеты; он не является read-only и допускается только на отдельном тестовом кабинете после проверки backup/restore.

## Включение потока и наблюдение

После заполнения приёмочного отчёта включить единый worker. Отдельные воркеры должны оставаться остановленными.

```bash
docker compose up -d worker
docker compose logs --since 10m worker
```

Сначала проверить ограниченный поток тестовой компании. Контролировать перезапуски, ошибки парсера/проверки записи, DLQ, задержку Kafka и ожидание PostgreSQL-блокировок. При неизвестной форме, дубле или неподтверждённой записи остановить worker, сохранить координаты события и состояние каталога, исправить причину до возобновления. Не переигрывать весь топик вслепую.

После запуска проверить метрику `unified_worker_ready` на порту метрик worker: значение `1` означает, что Kafka-клиенты и внутренние циклы запущены, но не доказывает успешность отдельных операций. При использовании Compose порт 9100 по умолчанию не публикуется на хост; проверять его из контейнера или сети мониторинга. Состояние журнала и отдельных операций:

```bash
docker compose run --rm --no-deps worker python -m scripts.integration_operations summary
docker compose run --rm --no-deps worker python -m scripts.integration_operations list --status failed
docker compose run --rm --no-deps worker python -m scripts.integration_operations show OPERATION_ID
```

Повтор после устранения причины и проверки актуальности входа создаёт новую связанную операцию; исходная запись и её DLQ остаются в журнале:

```bash
docker compose run --rm --no-deps worker python -m scripts.integration_operations retry OPERATION_ID --reason 'Описание исправления'
```

Сохранять `INTEGRATION_SOURCE_NAMESPACE` неизменным для одного источника между перезапусками. Новый namespace создаёт отдельную область дедупликации; не менять его и consumer group без плана переноса.

## Откат

1. Остановить все исполнители записи. Сохранить ошибки и координаты сообщений, состояние каталога до дальнейших действий.
2. Проверить, совместим ли предыдущий образ с текущей схемой БД и контрактами сообщений. Если нет — выполнить заранее проверенную процедуру восстановления, а не просто запуск старого кода.
3. Вернуть зафиксированный предыдущий образ/commit и конфигурацию. Не запускать два поколения worker одновременно.
4. Откат приложения не отменяет созданные группы, пользователей и изменённые ACL/виджеты. Сверить эти изменения и при необходимости восстановить каталог из резервной копии по отдельному плану.
5. Inbox, outbox, Kafka offsets и DLQ восстанавливаются/переигрываются только после сверки уже выполненных внешних действий. Подтверждённый Kafka offset означает запись события в inbox, а не завершение изменений в каталоге. При откате на старый образ, который не обрабатывает inbox/outbox, неисполненные операции и недоставленные результаты останутся в БД; требуется отдельный план их доведения или переноса.
