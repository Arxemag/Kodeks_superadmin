# Сквозная авторизация (SSO) фронт → кабинеты Кодекс

Задача: пользователь кликает «перейти в кабинет» на фронте и попадает в каталог
(`cabinet-0X.kodeks.expert`) **без** логин-формы. Логины/пароли на фронте и в
каталоге идентичны.

Здесь — что и почему. Кто что делает и в каком порядке — в [SSO_TASKS.md](SSO_TASKS.md).

---

## 0. Почему «передать куки фронту» не работает и не заработает

Куки жёстко привязаны к домену, который их выдал. Куки `cabinet-03.kodeks.expert`
может установить в браузер пользователя **только сам** `cabinet-03.kodeks.expert`
(или его родительский домен `*.kodeks.expert`). Сайт на другом домене
(`platforma.bravo-soft.ru` и т.п.) не может ни установить, ни «подсунуть» их —
это политика безопасности браузеров, она не настраивается ни в Кодексе, ни в
браузере, ни где-либо ещё.

Куки, которые отдаёт наш Auth API (`POST /api/expert/reg/{reg}?name=<uid>`),
предназначены для **сервер-серверных** запросов (бэк фронта → каталог,
наш воркер → каталог). Для браузерного SSO они бесполезны — в браузер
пользователя их не доставить.

Следствие: любые варианты SSO сводятся к одному — **куки в браузер должен
поставить сам домен kodeks.expert**. Ниже 3 способа этого добиться.

---

## 1. Вариант 1 (рекомендуемый): автологин через `login.asp` ✅ проверен вживую

Каталог штатно поддерживает вход POST-запросом с редиректом на целевую страницу:

```
POST https://cabinet-03.kodeks.expert/users/login.asp
Content-Type: application/x-www-form-urlencoded

user=<логин> & pass=<пароль> & path=/docs/?nd=606025000&infoboard=P000F

→ 307 Location: /docs/?nd=606025000&infoboard=P000F
  (сессионные куки ставит сам каталог по ходу цепочки; браузер оказывается
   в кабинете уже авторизованным)
```

Так как креды идентичны, фронт при клике делает **top-level переход** авто-сабмит
формой (браузер сам уходит на домен каталога — куки становятся first-party):

```js
function openCabinet(uid, psw, cabinetHost, targetPath) {
  const f = document.createElement('form');
  f.method = 'POST';
  f.action = `https://${cabinetHost}/users/login.asp`;
  f.target = '_blank';                          // или '_self'
  for (const [name, value] of Object.entries({ user: uid, pass: psw, path: targetPath })) {
    const i = document.createElement('input');
    i.type = 'hidden'; i.name = name; i.value = value;
    f.appendChild(i);
  }
  document.body.appendChild(f);
  f.submit();
  f.remove();
}
// openCabinet('n.krapivina', '<пароль>', 'cabinet-03.kodeks.expert',
//             '/docs/?nd=606025000&infoboard=P000F')
```

Хост кабинета для конкретного клиента фронт берёт по reg из нашего справочника
(`GET /api/expert/reg-services`).

**Обязательные условия (где обычно ошибаются):**

| Правило | Почему |
|---|---|
| Только top-level навигация (form.submit / window.location) | `fetch`/XHR на чужой домен = third-party, браузер отбросит куки |
| Не iframe | те же third-party ограничения |
| POST, не GET | пароль не должен попадать в URL / access-логи |
| Только HTTPS | пароль в теле запроса |

Плюсы: ничего не разворачивать, работает прямо сейчас.
Минус: пароль пользователя присутствует в JS фронта в момент клика
(передаётся один раз по HTTPS — эквивалент ручного входа пользователем).
Если это неприемлемо — вариант 2.

---

## 2. Вариант 2: SSO-шлюз на домене каталога (nginx + Auth API)

Идея: на домене `*.kodeks.expert` появляется маленький endpoint `/sso`,
который сам логинит пользователя в каталог и ставит куки. Пароль **вообще не
попадает в браузер** — ходят только одноразовые тикеты.

```
┌────────┐  1. клик «в кабинет»        ┌──────────────┐
│ Браузер│ ───────────────────────────▶│ Бэк фронта   │
│        │  2. 302 на /sso?ticket=XYZ  │ (создал ticket│
│        │ ◀───────────────────────────│  через наш API)│
│        │                             └──────────────┘
│        │  3. GET https://cabinet-03.kodeks.expert/sso?ticket=XYZ&path=/docs/?...
│        │ ───────────────────────────▶ nginx (домен каталога)
│        │                                │ proxy_pass /sso → Auth API
│        │                                ▼
│        │                             Auth API: проверил ticket,
│        │                             выполнил login.asp (креды берёт сам),
│        │                             вернул Set-Cookie + 302 path
│        │  4. Set-Cookie (first-party!) + 302 → /docs/?nd=...&infoboard=...
│        │ ◀───────────────────────────
│  в кабинете, авторизован ✔
└────────┘
```

Ключевой момент: nginx стоит **на домене каталога**, поэтому его `Set-Cookie` —
first-party, браузер их принимает. Сам nginx куки «не знает» — за ними он
проксирует запрос в наш Auth API, который логинится в каталог сервер-сайд
(у нас уже есть весь флоу: пароль пользователя достаётся через админа,
`AuthService.login(reg, name)`).

Эскиз конфига nginx (на сервере с каталогами, перед каждым cabinet-0X):

```nginx
# в server { listen 443 ssl; server_name cabinet-03.kodeks.expert; ... }
location = /sso {
    proxy_pass http://45.10.41.70:8000/api/expert/sso;   # наш Auth API
    proxy_set_header Host $host;                          # чтобы API знал, какой кабинет
    proxy_set_header X-Real-IP $remote_addr;
}
# остальной трафик — как раньше, в приложение каталога
```

Что потребуется доработать у нас (небольшой endpoint в auth-api):
`GET /api/expert/sso?ticket=...&path=...` →
проверка тикета (одноразовый, TTL ~60 сек, привязан к reg+uid) →
`AuthService.login(reg, name)` → ответ `302 Location: {path}` +
`Set-Cookie: <куки сессии>` (host-only — домен придёт из `Host`).

И endpoint выдачи тикета для бэка фронта:
`POST /api/expert/sso-ticket {reg, uid}` → `{ticket}` (хранится в памяти/БД с TTL).

Требования: доступ к nginx на серверах каталогов (или к DNS-зоне kodeks.expert —
см. вариант 2б). Плюсы: пароль не покидает серверы, тикет одноразовый.
Минусы: нужен деплой nginx-правила + ~100 строк кода у нас.

### 2б. Подвариант без правки серверов каталогов: поддомен `sso.kodeks.expert`

Если трогать серверы каталогов нельзя, но можно завести DNS-запись и TLS-серт:
поднимаем шлюз на `sso.kodeks.expert` (может указывать на наш 45.10.41.70).
Он делает то же самое, но куки ставит с атрибутом `Domain=.kodeks.expert` —
браузер будет отправлять их и на `cabinet-03.kodeks.expert`.
Каталогу всё равно, с каким Domain-атрибутом пришла кука — он читает имя/значение.

---

## 3. Вариант 3 (не рекомендуется): проксировать весь каталог под доменом фронта

Фронт-домен проксирует `/cabinet/*` → `cabinet-03.kodeks.expert`; тогда куки
каталога становятся куками домена фронта. На практике хрупко: абсолютные ссылки,
редиректы, `kodeks://`-ссылки, вебсокеты, кэширование — всё придётся переписывать
на лету. Поддержка дорогая, ломается при обновлениях каталога.

## 4. Сравнение

| Вариант | Пароль в браузере | Изменения инфраструктуры | Изменения у нас | Готовность |
|---|---|---|---|---|
| 1. Автологин `login.asp` | да, в момент клика (HTTPS) | нет | нет | **работает сейчас** |
| 2. SSO-шлюз (nginx) | нет | nginx-правило на каталогах | endpoint /sso + тикеты | ~день работы |
| 2б. Шлюз на поддомене | нет | DNS + TLS-серт | то же | ~день работы |
| 3. Полный прокси | нет | тяжёлые | нет | не рекомендуется |

Рекомендация: начать с варианта 1 (нулевая стоимость, проверен). Если политика
безопасности запретит пароль в JS — переходить на вариант 2/2б.
