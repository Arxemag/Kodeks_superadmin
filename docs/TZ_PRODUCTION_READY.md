# ТЗ: доведение Kodeks superadmin до промышленной эксплуатации

Дата: 26.10.2026. Статус: спецификация для реализации и приёмки.

## 1. Цель и границы

Доработать существующий сервис интеграции основной платформы с каталогом «Кодекс», чтобы повторная доставка событий, параллельная обработка, перезапуск процесса и временный отказ каталога не приводили к дублям групп, пропуску пользователей, потере событий и ложным сообщениям об успехе.

Результат — код, миграции, воспроизводимая сборка, автоматические проверки, подтверждённые прогоны на тестовом каталоге, инструкции развёртывания и восстановления. Наличие исходников или успешная сборка контейнера сами по себе не означают готовность.

Среда — закрытый контур. Переработка аутентификации, сетевой защиты и отдельный аудит безопасности в это ТЗ не входят. Существующие функции API должны сохраниться. Реальные производственные данные и каталог не изменяются автоматическими тестами.

Технологическая основа сохраняется: Python, FastAPI, Pydantic, PostgreSQL, SQLAlchemy, httpx, aiokafka, Docker Compose. Playwright используется для тех операций каталога, для которых подтверждена необходимость браузера. Замена стека целиком не требуется.

## 2. Предметная модель и обязательные правила

Компания основной платформы имеет стабильный `client_id`. `reg` определяет регистрацию и адрес каталога. Отдел определяется UUID, группа каталога — собственным ID, кабинет — ID каталога. Названия служат для отображения и первоначального поиска; после связывания идентичность сущности определяется ID.

Логическая цепочка: компания → отдел → группа каталога → разрешённые кабинеты; пользователь → группы его отделов → доступ к кабинетам.

Проектные решения для реализации:

1. `init_company` и существующий `sync_departments` передают полный снимок отделов компании. Частичное изменение требует отдельного явно версионированного контракта. Отсутствующее поле `departments` является ошибкой, а не пустым снимком. Перед внедрением это правило проверяется на сообщениях реального отправителя.
2. Явный пустой список отделов означает удаление всех отделов из управляемого состояния. Для старого контракта такой запрос отклоняется до внедрения согласованного признака `allow_empty_snapshot=true`. Пропуск поля и намеренная очистка не смешиваются.
3. Повтор одного события и повтор одинакового желаемого состояния не создают новых сущностей и не меняют уже достигнутый результат.
4. При переименовании отдела сохраняются UUID отдела и ID связанной группы; группа переименовывается с проверкой участников и ACL. Если каталог не поддерживает переименование, возвращается явная ошибка; создание новой группы вместо переименования запрещено.
5. Архивация отдела убирает его из управляемых назначений и ACL, но не удаляет физически группу и пользователя из каталога. Чужие назначения и ACL сохраняются.
6. `update-user-departments` задаёт полный желаемый набор управляемых групп пользователя. Группы, назначенные вне интеграции, сохраняются. Явный `departments=[]` снимает все назначения интеграции. По старому состоянию без истории владения группы автоматически не удаляются.
7. Создание групп принадлежит синхронизации компании. Обработчик пользователя не создаёт группу по одному названию: использует связь UUID отдела → ID группы. Если связь ещё не готова, операция ждёт завершения настройки компании в пределах заданного срока, затем получает диагностируемую ошибку зависимости.
8. `uid` — логин пользователя, `id` входящего события не считается автоматически внутренним ID пользователя каталога. Различие идентификаторов фиксируется на реальной форме и в контракте.

Эти решения являются требованиями целевой системы, а не утверждением о фактическом поведении отправителя сегодня. Несовместимость с отправителем устраняется до переключения продакшена; молчаливые догадки в коде запрещены.

## 3. Контракты событий и совместимость

Сохранить существующие имена топиков, URL API и поддержку плоского сообщения, envelope с `payload`, а также массива событий, если эти форматы используются отправителем. Внутри системы преобразовывать их в одну модель: `event_id`, `event_type`, `schema_version`, `client_id/reg`, `entity_id`, `source_revision` при наличии, `payload`, координаты Kafka и время получения.

Неизвестная версия, неизвестный тип, некорректный JSON и невалидный элемент массива должны получать явную ошибку и надёжно доставляться в DLQ. Элементы массива не пропускаются молча; их исходные индексы сохраняются.

Для новых событий обязателен стабильный `event_id`, сохраняющийся при повторе отправки. Для старых событий транспортный идентификатор — topic/partition/offset и индекс элемента массива. Он защищает от перечитывания Kafka, но не от повторной публикации того же действия с другим offset; этот случай закрывается сверкой желаемого и фактического состояния.

Один `event_id` с другим содержимым — конфликт, а не успешный дубль. Хранить fingerprint нормализованного содержимого. Повтор терминального события возвращает сохранённый результат.

Ключ inbox для нового контракта: namespace источника + `event_id`; для legacy: идентификатор Kafka-кластера/источника + topic + partition + offset + индекс элемента. Конфликт содержимого сохраняется отдельной записью ошибки со ссылкой на исходное событие, не заменяет его и не заставляет бесконечно перечитывать весь пакет. Ключ outbox: ID операции + тип результата + номер версии результата.

Порядок разных Kafka-топиков не определён. Для событий полного снимка требуется монотонная `source_revision` на компанию: устаревшее состояние не применяется. В режиме совместимости без ревизии гарантируется только порядок поступления в журнал интеграции; ограничение отражается в отчёте. Если отправитель может доставлять устаревшие снимки позже новых, внедрение ревизий — условие выпуска.

Для изменений пользователя отдельно фиксируется порядок на пользователя и область данных (поля профиля, назначения отделов). Старый retry не должен перезаписывать более новое состояние: применять ревизии источника либо сохранять последовательную очередь изменений этой сущности, не пропуская новые конфликтующие записи вперёд незавершённой старой. Исправление окончательно ошибочного события не блокирует очередь бесконечно: операция завершается явной ошибкой, а повтор выполняется после проверки актуальности. Порядок между созданием пользователя и его назначениями обеспечивается зависимостями.

Точные поля всех входов/выходов, типы ID, семантика null/отсутствия/пустого списка и примеры зафиксировать в `docs/KAFKA_TOPICS_AND_PAYLOADS.md`. Пароль остаётся обязательным при создании; для изменения необязателен, отсутствие сохраняет текущее значение.

## 4. Хранение данных

Сохранить существующие таблицы с миграцией данных. Разделить желаемое состояние, подтверждённое состояние каталога и ход операции. Названия таблиц ниже логические; окончательная SQL-схема и ограничения входят в поставку.

| Сущность | Обязательные данные и ограничения |
|---|---|
| Регистрации/каталоги | `reg`, `base_url`, `client_id` при известности, состояние связи, даты проверки |
| Отделы | `client_id`, UUID отдела, `reg`, исходное и нормализованное название, active/archived, ревизия источника; уникальность по компании и UUID |
| Связи групп | Отдел, идентификатор каталога, ID группы, последнее подтверждённое название, состояние связывания, происхождение created/adopted; ID группы уникален в пределах каталога, связь нескольких отделов с одной группой по умолчанию — конфликт |
| Кабинеты и доступ | ID кабинета в каталоге, название для отображения, желаемые связи отдел → кабинет, подтверждённые ACL, сведения о владении интеграцией |
| Пользователи/назначения | Идентификаторы платформы при наличии, логин, внутренний ID каталога, желаемые отделы, назначения групп интеграцией и результат последней проверки |
| Inbox / операции | Уникальный ключ события, fingerprint, исходные координаты и индекс массива, тип, сущность, вход, версия, этап, статус, попытки, следующая попытка, lease/fencing token, ошибки, результат и даты |
| Outbox | Уникальный ключ исходящего результата, операция, topic, key, payload, состояние и попытки доставки |

Не создавать вторую мастер-базу паролей пользователей: постоянное хранение копии пароля не требуется для сопоставления сущностей. Для отложенного исполнения допускается хранение исходного входа в журнале операции; срок хранения входа и результатов задаётся конфигурацией. Очистка не удаляет незавершённые операции и записи с недоставленным outbox. Срок дедупликации должен покрывать согласованный период возможного переигрывания Kafka; после его истечения всё равно работает сверка состояния.

Состояния операции: `received`, `waiting_dependency`, `running`, `retry_wait`, `verifying`, `succeeded`, `failed`, `conflict`. «Частично выполнено» хранится как состояние этапов незавершённой операции; не считается успехом. Успех разрешён только после проверки всех обязательных действий. Ошибка отправки ответа не отменяет уже подтверждённые изменения каталога.

## 5. Интеграция с каталогом

Собрать HTTP, GraphQL, HTML и браузерные операции за единым адаптером. Бизнес-обработчики не должны сами разбирать HTML или конструировать административные формы. У отдельных воркеров и единого воркера одна реализация бизнес-правил.

Адаптер предоставляет операции: проверка сессии, чтение групп, поиск/чтение/создание/изменение пользователя, создание/переименование группы, чтение кабинетов, чтение/изменение ACL, чтение/изменение виджетов. Возвращает проверяемые типизированные результаты с ID, а не только HTTP-код.

Обязательная особенность протокола «Кодекса», подтверждённая владельцем: сохранение административной формы требует передать одним запросом весь предусмотренный этой формой набор текущих параметров с внесёнными изменениями. Передача только изменённых полей вместо полной формы недопустима. Это требование каталога, а не дефект архитектуры.

Последовательность записи: получить актуальную полную форму в действующей сессии → сохранить исходные параметры → наложить нужные изменения → отправить полную форму одним запросом сохранения → перечитать и проверить результат. Сохранять незатронутые значения, обязательные скрытые и служебные поля, пустые значения и повторяющиеся параметры, например несколько `grp`. Представление формы не должно терять повторяющиеся имена при преобразовании в обычный словарь. Правила отсутствующих checkbox и параметры кнопки сохранения воспроизводить по действующей форме каталога. Если полнота формы не подтверждена, запись запрещена. Это относится и к HTTP-пути, и к сохранению через браузер.

Из-за полной перезаписи формы операции чтение → изменение → сохранение сериализуются в пределах одного каталога. Не использовать устаревший снимок формы из предыдущей попытки. Сериализация интеграции сама по себе не исключает параллельную ручную правку: при наличии механизма версии формы проверять его, иначе ограничение и порядок совместной работы фиксируются в runbook.

Для каждой операции определить признаки правильной страницы, страницы входа, отсутствующей сущности, бизнес-ошибки, неподдерживаемой разметки и неполного списка. HTTP 200 сам по себе не доказывает успех. Ошибка распознавания никогда не означает «сущностей нет».

HTML разбирать DOM-парсером с покрытием реальных форм: пробелы вокруг `=`, кавычки и их отсутствие в допустимых атрибутах, вложенные теги, HTML entities, кириллица, кодировка ответа, пагинация. Список групп считается полным только после обработки всех страниц/подтверждённого отсутствия пагинации. Признаки разметки и сценарии поведения подтверждаются сохранёнными обезличенными ответами тестового каталога.

Единая нормализация названий: Unicode NFC, декодирование HTML entities при чтении HTML, NBSP → пробел, схлопывание пробелов, trim, casefold. Не удалять знаки препинания и не заменять автоматически «ё» на «е». Несколько совпадений после нормализации — конфликт; нельзя выбирать последнее или случайное.

Сессии изолировать по каталогу и учётной записи. Таймауты разделить на подключение, запрос и операцию; отладочный уровень логов не меняет бизнес-таймаут. Ограничение конкуренции учитывать отдельно для HTTP и браузера. Circuit breaker изолировать по каталогу, чтобы отказ одного не останавливал остальные.

После сетевого таймаута записи её результат считается неопределённым: сначала перечитать состояние, затем решать, нужен ли повтор. Отсутствие гарантии идемпотентности каталога запрещает слепой повтор POST создания. Если невозможно определить, было ли создание применено, операция останавливается с явным состоянием для разбора, а не создаёт ещё одну сущность.

## 6. Сценарии

### 6.1. Настройка компании и отделов

1. Проверить контракт, компанию, регистрацию и ревизию; сохранить желаемое состояние и операцию.
2. Получить исключительное право изменения каталога компании, проверить сессию и полноту чтения.
3. Для каждого отдела сначала использовать сохранённый ID группы. Если связи нет, найти единственное совпадение названия и принять существующую группу. При отсутствии создать, перечитать и сохранить ID; при неоднозначности остановить зависимые действия с конфликтом.
4. По найденным ID кабинетов построить желаемые управляемые ACL. Отсутствующий или неоднозначный кабинет — явная ошибка, а не пропуск.
5. Рассчитать разницу управляемых ACL, наложить её на актуальную полную форму и передать все параметры формы одним запросом сохранения. Сохранить назначения вне интеграции; удалённые связи интеграции снять. Посторонние поля сохранить с текущими значениями.
6. Перечитать группы и ACL. Только при совпадении с планом пометить состояние применённым и операцию успешной.

Для существующих ACL перед первой записью сохранить снимок и определить владение. При невозможности отличить старые назначения интеграции от ручных автоматическое удаление запрещено: требуется подготовленная таблица соответствий в миграционном плане.

Принятие существующей группы связывает её ID с отделом, но не объявляет прежних участников и ACL собственностью интеграции. В миграционном плане для принятой группы отдельно фиксируются разрешение на переименование и перечень управляемых связей. Без такого решения переименование ручной группы останавливается конфликтом; её прежние назначения сохраняются.

### 6.2. Пользователи

1. Проверить регистрацию и идентификаторы; получить подтверждённую сессию каталога.
2. Найти пользователя по согласованному ключу и проверить идентичность возвращённой формы. Пустая форма создания и страница входа не означают существующего пользователя.
3. При создании существующего пользователя сверить состояние и применить необходимые изменения. При обновлении отсутствующего пользователя вернуть `USER_NOT_FOUND`, не создавать его неявно.
4. При изменении сохранить не переданные платформой поля, внутренний ID каталога и неуправляемые группы. В запрос к каталогу включить полную актуальную форму с наложенными изменениями, включая незатронутые параметры. Не подставлять логин вместо внутреннего ID без подтверждённого контракта.
5. После записи перечитать пользователя и проверить все изменённые поля, которые каталог позволяет читать, и итоговый набор групп. Для пароля определить подтверждаемый способ проверки на тестовом каталоге; непроверяемые поля явно описать, не выдавать отправку POST за доказательство сохранения.
6. Успех и счётчики успешных операций выставлять после проверки. Повторная проверка не должна повторно увеличивать счётчик той же операции.

### 6.3. Назначение отделов пользователю

Использовать UUID отделов и сохранённые ID групп. Название во входе служит для диагностики расхождений. Событие, пришедшее раньше создания пользователя или настройки компании, сохраняется в `waiting_dependency`, не теряется и повторяется после готовности зависимости.

Итоговые группы: текущие группы минус ранее назначенные интеграцией плюс желаемые группы интеграции. Если принадлежность старой группы интеграции неизвестна, сохранить её и зарегистрировать расхождение. После записи сравнить фактическое членство с рассчитанным набором.

### 6.4. Уточнение кабинета

Сохранить поддержку «Эколога». До первой записи построить и проверить полный план: дерево кабинетов, все вопросы, варианты ответов и целевые виджеты. Неизвестный вопрос/ответ, отсутствующий или неоднозначный раздел — ошибка плана. Нельзя удалить виджеты по части вопросов и затем объявить полный успех.

«Выбрать всё» сохраняет существующие виджеты вопроса; системные элементы навигации сохраняются всегда. После изменения перечитать виджеты и проверить результат. При сбое на середине сохранить этапы и продолжить после сверки состояния.

Текущий контракт выполняет общее изменение кабинета каталога; `userId` — корреляция ответа, а не изоляция пользовательской копии. До приёмки подтвердить, что это соответствует платформе. Создание индивидуальных копий кабинетов не входит в текущий контракт и требует отдельного требования, если они нужны.

`dry-run` не изменяет каталог и не публикует обычный `cabinet-corrected`, имитирующий выполненную запись. План и результат проверки доступны как результат операции. Для боевого режима сохранить действующие поля ответа; расширение статусов/версий согласовать с потребителем и проверить совместимость.

### 6.5. Включение и отключение регистрации

Существующие обработчики являются заглушками. Считать их реализованной функцией запрещено.

До реализации документировать на реальном тестовом каталоге: что включается/отключается, какая операция каталога это выполняет, как проверяется результат, что означает `oldReg` и требуется ли перенос данных. По одному наличию этих полей нельзя автоматически переносить БД, группы или ACL.

Обязательное условие приёмки: либо подтверждённый контракт и реализованная операция с проверкой результата, либо документированное исключение функции из согласованного объёма выпуска с явной ошибкой `NOT_IMPLEMENTED` для входящего события. Молчаливый успех и commit без сохранённой ошибки запрещены. Семантика этого потока, снимков отделов и общего изменения кабинета подтверждается на этапе фиксации контрактов.

## 7. Kafka, конкуренция и восстановление

Целевая модель: Kafka → долговечный inbox в PostgreSQL → исполнитель операций → сверка каталога → outbox → Kafka.

Offset входа подтверждать после успешной транзакционной записи всех элементов сообщения в inbox, включая записи об ошибках формата. До этого подтверждение запрещено. Завершение действий каталога происходит отдельно; последующий отказ обрабатывается из inbox. Транспортное подтверждение не означает бизнес-успех.

Запись подтверждённого состояния каталога, терминального статуса операции и соответствующих сообщений outbox выполняется одной транзакцией PostgreSQL. Сбой между проверкой внешнего результата и этой транзакцией приводит к повторной сверке, а не к потере ответа. Это требование проверяется отдельным crash-тестом.

При переходе на inbox нельзя оставлять старую модель частично: все подписанные топики используют единое правило. Сбой записи inbox оставляет сообщение неподтверждённым. Сбой outbox не теряет ответ и не заставляет повторно изменять каталог.

Чтение Kafka ведётся отдельно от длительных HTTP/браузерных операций. Не требовать непрерывности числовых offsets: подтверждать только фактически доставленные и сохранённые записи, не перескакивая несохранённую запись. Учитывать rebalance и отзыв партиций; не подтверждать чужую партицию. Ограничить backlog и при недоступности БД/переполнении приостанавливать приём.

Для операций одного каталога использовать сериализацию записей между всеми экземплярами worker, а не только `asyncio.Lock` внутри процесса. Конкретный механизм PostgreSQL lock/lease описать и протестировать: уникальный владелец, продление, обнаружение потери владения, запрет новым этапам записи после потери lease. После takeover сначала сверять результат незавершённого внешнего действия. Слепое создание при неопределённом исходе запрещено. Разные каталоги обрабатываются параллельно в пределах конфигурации.

Ключ сериализации — стабильный `catalog_id`, общий для всех регистраций, компаний и алиасов URL одного административного каталога. Правила канонизации и объединения алиасов фиксируются в данных. Проверить одновременные операции двух `reg`, указывающих на один каталог.

Выбор следующей операции детерминирован; ревизия проверяется повторно под блокировкой непосредственно перед записью. Принятая ревизия и подтверждённо применённая ревизия хранятся раздельно. Ожидание зависимости не удерживает блокировку и не мешает исполнению события, создающего эту зависимость; конфликтующие изменения одной сущности сохраняют порядок.

Fencing token в БД не останавливает уже отправленный запрос каталога. Новый исполнитель не начинает конфликтующие внешние записи, пока исход старого запроса не установлен. Если завершение или достоверную сверку установить нельзя, фиксируется неопределённый исход и требуется разбор операции. Приёмочный тест: старый worker теряет lease после отправки POST, новый получает владение, старый запрос завершается с задержкой; дублей и перезаписи нового состояния быть не должно.

Inbox защищает от повторного планирования события. Он не создаёт распределённую транзакцию с каталогом: обязательны проверка результата каждого шага и восстановление после сбоя между внешней записью и локальным сохранением.

Outbox доставляется как минимум один раз. Исходящий `event_id` стабилен при повторе; потребитель должен переносить дубли. Если старый потребитель не поддерживает дедупликацию, это фиксируется и устраняется до переключения соответствующего потока.

Ошибки делить на временные, зависимости, конфликты и окончательные. Повторы с backoff/jitter, пределом попыток и общего времени задаются конфигурацией. Неожиданное исключение сохраняется в операции; не теряется за одной записью лога. DLQ доставляется через outbox. Повтор из DLQ — явная команда с сохранением связи с исходной операцией и проверкой текущего состояния.

## 8. Миграция существующего состояния

1. Сделать резервную копию БД и выгрузку групп, пользователей, членства, ACL, дерева кабинетов и полных конфигураций виджетов каталогов, затрагиваемых выпуском. Проверить восстановление на отдельной среде, включая возврат удалённых виджетов. Если каталог не позволяет восстановить такие данные, до включения correct-cabinet требуется проверенный штатный backup/restore каталога.
2. Новые таблицы и поля добавить совместимыми миграциями; миграции версионируются и учитывают уже применённые версии. Seed не очищает существующий справочник по умолчанию.
3. Выполнить read-only инвентаризацию: сопоставить отделы с группами, выявить дубли, неоднозначные кабинеты, отсутствующие сущности и незавершённые связи.
4. Для каждого дубля подготовить план: выбранный ID, участники, ACL, связанные отделы. Автоматически удалять или объединять существующие группы по названию запрещено. Разрешение существующих дублей оформляется отдельным проверяемым миграционным действием.
5. Заполнить связи ID и сведения о владении; неопределённости вынести в отчёт. Для компаний с конфликтами запись не включать до разрешения.
6. Остановить старых исполнителей перед переключением. Сохранить consumer group/позиции; исключить одновременную работу старого и нового пути записи. При несовместимом контракте использовать согласованную версию топика/события.

## 9. Сборка, эксплуатация и диагностика

- Один поддерживаемый Python и воспроизводимое окружение: manifest/lock с точными прямыми и транзитивными зависимостями. Production и test/dev зависимости разделены. Версии Python, Chromium и Playwright проверены совместно; плавающий `latest` исключён.
- На чистом окружении одной документированной последовательностью выполняются установка, тесты, сборка, миграции и запуск. Локальная `.venv` не является частью поставки.
- API и worker используют согласованные адреса/порты. Изменение `PORT` не нарушает внутреннюю связь. Настройки, обязательные значения и разумные пределы concurrency/timeouts валидируются при старте.
- Разделить liveness и readiness. Readiness проверяет доступность БД и актуальность схемы; состояние Kafka и исполнителя проверяется для worker. Недоступность одного каталога видна отдельно, без остановки остальных каталогов.
- Graceful shutdown прекращает приём новых работ, сохраняет состояние и корректно закрывает клиентов. Время завершения ограничено; незавершённые операции восстанавливаются из журнала.
- По ID операции доступны состояние, этапы, попытки, ошибка, ожидаемое и фактическое состояние, следующий повтор и связь с входящим событием. Предоставить read-only API/CLI просмотра и CLI повторного запуска/сверки с документированными параметрами.
- Метрики: приём/дубли/ошибки контракта, длина и возраст inbox/outbox, операции по статусам, время обработки, ошибки каталога, ожидание зависимостей, конфликты сопоставления, расхождения проверки, доставка DLQ. Не использовать ID операций/пользователей как labels метрик.
- Логи связывают событие, операцию, компанию, этап и ошибку. Числовые пороги оповещения и время хранения фиксируются в конфигурации выпуска.
- CI: тесты → сборка → миграции на тестовой БД → интеграционные проверки → публикация версии. Deploy ожидает readiness и выполняет smoke; успешный `docker compose up` не завершает проверку.

## 10. Обязательная проверка

Использовать три уровня: unit для бизнес-правил, интеграционные тесты с PostgreSQL/Kafka и HTTP-fixtures, приёмочный прогон на отдельном реальном каталоге. Stub, который всегда сохраняет POST, не заменяет проверку контракта каталога.

| Проверка | Ожидаемый результат |
|---|---|
| Существующая группа с тем же названием | Принят её ID; новых групп нет |
| Название с NBSP, регистром, повторными пробелами | Однозначное нормализованное совпадение; дубликат не создаётся |
| Две существующие группы с одинаковым нормализованным названием | Конфликт, без случайного выбора и новых групп |
| Два отдела с одинаковым нормализованным названием | Явный конфликт до записи, если нет отдельно подтверждённой модели общего доступа |
| Два worker и одновременные события на один каталог | Группа/пользователь созданы один раз; записи сериализованы |
| HTML с `href =`, вложенными тегами, пагинацией | Полный корректный список |
| Login HTML/неизвестная разметка вместо списка | Ошибка чтения; создания «отсутствующих» сущностей нет |
| Отсутствующий пользователь: 404, пустая форма, согласованный ответ 200 | Состояния различаются; создание выполняется только при подтверждённом отсутствии |
| POST пользователя вернул 200 с бизнес-ошибкой | Нет `succeeded` и ложного счётчика успеха |
| Изменено одно поле пользователя или один ACL | В одном запросе сохранения отправлена полная актуальная форма; пустые, скрытые, повторяющиеся и незатронутые параметры сохранены согласно протоколу |
| Форму не удалось полностью прочитать | Запись не отправляется; нет потери существующих параметров |
| Пароль отсутствует в update | Текущий пароль сохранён |
| Переименование отдела | ID группы, участники и не затронутые права сохранены |
| Удаление отдела/явная очистка назначений | Удалены только управляемые связи; ручные назначения сохранены |
| Событие пользователя раньше настройки компании | Сохранено ожидание, затем выполнено без потери |
| Старая ревизия пришла после новой | Новое состояние не перезаписано |
| Некорректный JSON, неизвестный тип, смешанный массив | Диагностируемая ошибка каждого элемента, доставка в DLQ без остановки приёма |
| Offsets с пропусками, rebalance | Нет зависания на отсутствующем номере и пропуска несохранённой записи |
| Повтор event_id и конфликт его содержимого | Повтор не исполняется заново; конфликт явно зарегистрирован |
| Сбой Kafka/БД/каталога на каждом этапе | Нет потери принятой работы; после восстановления достигнуто проверенное состояние либо явная окончательная ошибка |
| Сбой после внешнего POST до локального commit | Сначала сверка, повторного создания нет |
| Недоступен выходной топик/DLQ | Outbox остаётся недоставленным и позже отправляется; каталог повторно не изменяется |
| Уточнение: неизвестный вопрос/ответ, отсутствующий кабинет | План отклонён до первой записи; обычного ответа об успехе нет |
| Dry-run | Изменений и боевого сообщения об успехе нет; план доступен |
| Регистрация enable/disable | Подтверждённое изменение либо явная ошибка согласно согласованному объёму |

Нагрузочный минимум: 1 000 событий на 10 компаний, включая 100 параллельно предложенных событий для одной компании и повторную доставку не менее 20% событий. Прогон выполняется на изолированной интеграционной среде; нагрузка на реальный каталог согласуется с его ограничениями. Ноль дублей, потерь и ложных успехов; все принятые операции имеют объяснимое состояние. Фактическую пропускную способность и p95/p99 измерить и включить в отчёт; достаточность сравнить с измеренным пиком отправителя. Произвольное обещание скорости без измерения не допускается.

## 11. Этапы выполнения и результаты

1. **Фиксация контрактов.** Снять обезличенные ответы каталога, примеры событий отправителя, подтвердить идентификаторы, семантику снимков, порядок ревизий и enable/disable. Результат: контракт, fixtures, список расхождений; критические неизвестные закрыты.
2. **Адаптер и данные.** Единое чтение/запись каталога, нормализация, проверка результата, миграции связей ID и желаемого состояния. Результат: тесты реальной разметки и план миграции без автоматического удаления дублей.
3. **Надёжное исполнение.** Inbox/outbox, зависимости, сериализация, повторы и восстановление. Результат: интеграционные проверки с остановкой процессов и отказами.
4. **Функциональная приёмка.** Все бизнес-сценарии на тестовом каталоге, сверка фактических групп/пользователей/ACL/виджетов. Результат: отчёт с доказательствами.
5. **Выпуск.** Версионированный образ, миграции, инвентаризация, проверенный runbook, пробное переключение и восстановление. Результат: комплект, который можно установить на прод по инструкции.

Код разделять по фактической ответственности: контракты, бизнес-сценарии, репозитории, адаптер каталога, транспорт и исполнение. Не плодить самостоятельные копии OffsetTracker/retry/обработчиков. Не сохранять старую функциональность только в устаревшем отдельном воркере.

## 12. Критерии готовности к продакшену

Все обязательные пункты должны иметь статус PASS в `docs/PRODUCTION_ACCEPTANCE.md`. PARTIAL, непроверенный контракт каталога, известная потеря сообщений или ложный успех запрещают маркировку релиза как production-ready.

В отчёте указать commit, версии зависимостей/образов, миграции, параметры и среду проверок, команды, результаты, доказательства состояния до/после, ограничения и решение по enable/disable. Невыполненные проверки не заменять фразой «должно работать».

Матрица приёмки связывает каждый пункт ТЗ (номер раздела и порядковый номер требования) с тестом или проверяемым доказательством. До выпуска в комплекте конфигурации фиксируются числовые значения backlog, времени ожидания зависимостей, предела повторов, retention и порогов оповещения; незаполненные значения и неограниченные ожидания не допускаются.

Комплект поставки:

- исходный код, миграции, lock-файл, тесты и обезличенные fixtures;
- Dockerfile/Compose, CI/CD, `.env.example` без привязки к одной машине;
- актуальные архитектура, контракты событий, схема БД и правила владения данными;
- `docs/PRODUCTION_ACCEPTANCE.md` с результатами всех проверок;
- `docs/PRODUCTION_RUNBOOK.md`: установка с нуля, обновление, просмотр операции, разбор DLQ, повтор, сверка состояния, остановка и восстановление;
- отчёт инвентаризации и миграционный план для существующих данных;
- проверенная инструкция отката приложения и отдельная процедура восстановления данных. Возврат старого образа сам по себе не откатывает изменения каталога; перед откатом исполнители останавливаются, незавершённые операции и совместимость схемы проверяются.

Предпродовая проверка: чистое развёртывание → миграции → readiness → создание/повтор пользователя → назначение отделов → сверка ACL → повтор события → перезапуск в середине операции → восстановление → проверка outbox/DLQ. На проде сначала одна тестовая компания, затем ограниченная партия и расширение после сверки. Тестовые события не направляются в действующие компании без разрешённого сценария.

Итоговый критерий: для каждого принятого события известно, что требовалось изменить, что подтверждено в каталоге и почему операция завершилась либо ожидает продолжения; повтор и перезапуск не создают лишних групп и пользователей.
