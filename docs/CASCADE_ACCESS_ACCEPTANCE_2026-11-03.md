# Проверка каскадного доступа к кабинетам

Исправления: `90ec7708cbf95ace678ce9fe7ae6235e222f8cb1` и
`ffe42981caf996cb219fd78e83d8c266ed207707`, ветка `release`.

Ранее `init_company` добавлял группы подразделений только в ACL главного кабинета.
Вложенные кабинеты не входили в расчёт. Обычный пользователь успешно проходил
SSO в три главных кабинета, но при открытии вложенной страницы `P003I` получал
видимый отказ в доступе. Проверка воспроизведена до изменения прав.

Теперь перед любыми изменениями читается граф всех ссылок `LinksWidget` одним
запросом. Доступ распространяется по всему каскаду, общие страницы получают
объединение групп. Обратная навигация и переходы в другие главные кабинеты не
расширяют выдачу. Дочерние страницы определяются по ID, одинаковые названия
не создают неоднозначности. Отсутствующая связанная страница, повреждённые
данные и превышение лимита прерывают обработку до записи.

На реальной форме подтверждено: `acl_infoboard_*_view` регулирует доступ,
`acl_infoboard_*` — редактирование. Каскад добавляет только доступ. Предыдущие
правила редактирования главных кабинетов сохранены; матрица редактирования
остаётся отдельной задачей.

## Проверка на сервере

Для reg `465304` текущая структура портала сверена с полным снимком:
32 подразделения, 23 назначенных кабинета, компания 31. «Кабинет СМК» явно
отложен до загрузки владельцем; подмена другим кабинетом не выполняется.

В загруженном наборе 620 страниц. Из 22 доступных главных кабинетов достижимы
613 страниц. Семь страниц директора по закупкам не назначены структурой и
не включаются в выдачу. Три кабинета проверяемого пользователя имеют каскады
51, 12 и 33 страницы; с учётом общих страниц — 94 уникальные страницы.

План изменил 591 поле доступа. Свежим чтением подтверждены все 1240 полей ACL
и флаги активации. Все 620 настроек редактирования, прочие настройки формы,
существующие ручные права, привязки 32 групп и ownership других регистраций
сохранены. Подтверждено 635 управляемых полей для этой регистрации.

Кодекс сохранил форму, но не ответил за 60 секунд. Поэтому операция 20
осталась в журнале с `ACL_WRITE_UNCERTAIN`. После полной сверки фактического
состояния восстановлен учёт управляемых прав; повторный POST не выполнялся.
Историческая ошибка не переписывалась. Идемпотентность проверена реальным
вызовом планирования ACL с запретом сохранения и записи в БД: PASS,
попыток сохраняющего POST — 0.

Дополнительное исправление проверяет всю форму после таймаута или 5xx.
Только строго подтверждённое состояние позволяет завершить обработку успешно
и записать ownership. При несовпадении или неудачном чтении сохраняется
`ACL_WRITE_UNCERTAIN`; автоматического повторного POST нет. Эти сценарии
покрыты восемью дополнительными тестами.

Основной конфиг nginx, TLS и конфигурация портала сверены по контрольным
суммам и не менялись.

Для полного браузерного прогона используется отдельное CDP-подключение
`ws://chromium:3000?timeout=900000`: штатный двухминутный лимит служебного
браузера недостаточен для последовательной проверки 94 страниц. Рабочая
настройка `CONNECTION_TIMEOUT=120000` не изменялась. Проверка ждёт загрузки
фрейма конкретного `infoboard`, проверяет видимый контент и сообщения об отказе;
список метаданных GraphQL не считается доказательством доступа.

Полный браузерный прогон завершён: PASS. В свежем сеансе выполнен реальный вход
пользователя портала компании 31, проверена личность в Auth-cookie Кодекса,
затем открыты все 94 уникальные страницы трёх каскадов. Каждая страница вернула
HTTP 200 и показала ожидаемый контент фрейма без формы входа или отказа в доступе.
Два главных кабинета открыты нажатием ссылок портала; для метролога использован
тот же API портала выдачи одноразовой SSO-ссылки, поскольку тест не нашёл
единственную видимую ссылку. Подмена пользователя служебной учётной записью
не применялась.

Отрицательная проверка: неназначенный «Кабинет Технолог» (`P006U`) показал отказ
в доступе. Это проверка реальной страницы, а не списка метаданных.
