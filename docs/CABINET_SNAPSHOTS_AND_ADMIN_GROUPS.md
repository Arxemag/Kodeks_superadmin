# Снимки кабинетов и группы-дубли

Две доработки от 2026-08-19: повторное уточнение кабинета с возвратом виджетов
и связь «пользователь → кабинет» в обход отделов. Отложенное — в [BACKLOG.md](BACKLOG.md).

---

## 1. Повторное уточнение: эталон вместо текущего состояния

### Что было

`editConfig` в каталоге — полная замена набора виджетов. Уточнение считалось от **текущего**
состояния борда, поэтому работало только на сужение: если клиент во второй раз выбирал больше
вариантов, вернуть удалённые виджеты было нечем.

### Что стало

При первом проходе снимается **эталон** каждого борда дерева, и дальше каждое уточнение
считается от него. Повторный опросник умеет и убирать, и возвращать.

```
1-й опросник:  эталон [А, Б, В, Назад] ──▶ выбрано {А} ──▶ на борде [А, Назад]
                     │  (снят и сохранён в БД)
2-й опросник:        └──────────────────▶ выбрано {А, Б} ──▶ на борде [А, Б, Назад]
                                                                    ▲
                                                       Б восстановлен из эталона
```

### Хранилище

Таблица `cabinet_snapshots`, миграция [005_cabinet_snapshots.sql](../scripts/migrations/005_cabinet_snapshots.sql),
модуль [snapshot_store.py](../services/infoboards_service/snapshot_store.py).

| Колонка | Тип | Описание |
|---|---|---|
| `reg` | varchar(50) | Код рега |
| `board_id` | varchar(100) | Идентификатор борда (напр. `P000M`) |
| `title` | text | Заголовок на момент снимка — для чтения глазами |
| `config` | jsonb | Полный конфиг: `id`, `author`, `title`, `searchString`, `hiddenOnStartPage`, `widgets` |
| `created_at` | timestamptz | Когда снят |

Уникальный индекс по `(reg, board_id)`; запись идёт через `ON CONFLICT DO NOTHING`.
**Эталон пишется один раз и никогда не перезаписывается** — это и есть точка отсчёта.

Имя таблицы настраивается через `DB_TABLE_CABINET_SNAPSHOTS`. Создаётся обычным
`python scripts/init_db.py`.

### Как считается итоговый набор

Функция `plan_widgets_from_snapshot` в [cabinet_edit.py](../services/infoboards_service/cabinet_edit.py):

1. Порядок берётся из эталона.
2. Виджет, который сейчас на борде **есть**, переносится как есть — со своим `widgetUuid`,
   иначе каталог создаст дубль.
3. Виджет из эталона, которого сейчас **нет** и который не в списке на удаление, возвращается
   с `widgetUuid: ""` — новый uuid присвоит каталог. (Так же поступает проект-конструктор:
   `payloads.py` создаёт все виджеты с пустым uuid.)
4. Системные виджеты («Вернуться назад», «Справочная информация») не удаляются никогда.
5. Виджеты, появившиеся на борде **после** снимка, сохраняются в конце — ручные правки
   в каталоге не теряются.

Запись в каталог идёт только если что-то реально меняется (есть удаляемые или возвращаемые).
Повторный прогон с теми же ответами по-прежнему не делает ни одного запроса на запись.

### Важная сопутствующая правка

`editConfig` заменяет конфиг борда целиком, а мы читали и отправляли не все поля. Теперь
`hiddenOnStartPage` **читается и возвращается обратно** — иначе каждое уточнение снимало бы
с под-кабинета скрытие, и он всплывал бы плиткой на стартовой странице ТЭ. Поле подтверждено
как часть `ConfigInput` по рабочему коду проекта-конструктора.

### Снимок снимается и в dry-run

Осознанно: чтение безопасно, а к моменту боевого прогона эталон уже будет в БД.
Сейчас на проде `CORRECT_CABINET_DRY_RUN=true` — то есть первые же сообщения наполнят
таблицу снимками, ничего не изменяя в каталоге.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CORRECT_CABINET_RESTORE` | `true` | Считать от эталона (умеет возвращать). `false` — прежнее поведение, только удаление |
| `DB_TABLE_CABINET_SNAPSHOTS` | `cabinet_snapshots` | Имя таблицы снимков |

Если снимка для борда нет (борд появился позже, или восстановление выключено) — работает
прежняя логика от текущего состояния. Обратная совместимость сохранена.

## 2. Связь «пользователь → кабинет» в обход отделов

### Ограничение, из которого всё следует

Прямой связи «пользователь → кабинет» в каталоге не существует: ACL кабинета оперирует
**только группами** (`{"kw":["31","32"]}` — это id групп). Поэтому связь строится через
группу, но такую, которая не привязана к отделам.

### Решение

Для отдела с указанным главным пользователем создаётся **группа-дубль** с суффиксом:
`Эколог` → `Эколог-админ`. Она выдаётся конкретному человеку поверх его текущих групп.

Входящий payload `init_company` / `sync_departments` — новое **необязательное** поле:

```json
{
  "id": 67,
  "reg": "465302",
  "companyName": "ООО Ромашка",
  "departments": [
    {
      "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
      "title": "Эколог",
      "modules": ["Кабинет эколога"],
      "mainUser": "n.krapivina"
    }
  ]
}
```

`mainUser` — uid пользователя в каталоге. Без него поведение прежнее, ничего не создаётся.

Обработка — `_sync_admin_groups` в [init_company_service.py](../services/infoboards_service/init_company_service.py):
группа создаётся, если её ещё нет (поиск без учёта регистра и лишних пробелов), затем выдаётся
пользователю **поверх** имеющихся групп. Если пользователь в каталоге ещё не заведён —
пишется предупреждение, init_company не падает.

### Защита от затирания — главное здесь

`handle_update_departments` заменяет список групп пользователя целиком, списком по отделам.
Группа-дубль в этом payload не приходит, поэтому без защиты она была бы затёрта первым же
обновлением отделов, и доступ **молча** пропал бы.

Теперь при замене групп сохраняются те, чьё название оканчивается на `ADMIN_GROUP_SUFFIX`
([users_service/service.py](../services/users_service/service.py), `_preserved_admin_groups`).
Обычные группы отделов по-прежнему заменяются целиком.

Пустой суффикс отключает механизм — иначе под правило попали бы все группы подряд.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ADMIN_GROUP_SUFFIX` | `-админ` | Суффикс группы-дубля. Он же признак «группа выдана вне отделов» |

### Чего эта доработка НЕ делает

**Права на редактирование не выдаются.** Группа-дубль попадает в ACL кабинета так же, как
обычная — оба поля (`acl_infoboard_{id}` и `_view`) получают одинаковый список.

По модели доступа каталога (уточнено заказчиком 2026-08-19) **по умолчанию все кабинеты
закрыты и на просмотр, и на редактирование, а группы в ACL открывают просмотр**. Значит,
группа-дубль сейчас даёт своему владельцу ровно то же, что обычная группа отдела, — просмотр.

Редактирование выдаётся, судя по всему, через глобальное поле `acl_infoboardsedit`, но это
требует проверки на стенде: поле общее на весь каталог, то есть даст правку **всех** инфобордов
сервиса, а не только своего. См. [BACKLOG.md, пункт 1](BACKLOG.md).

То есть сейчас механизм даёт **адресную выдачу доступа к кабинету конкретному человеку мимо
отделов** и переживает синхронизацию отделов. Разница в уровне прав появится после исследования.

## Что нужно сделать при выкатке

1. **Создать таблицу:** `python scripts/init_db.py` (миграция `005` идемпотентна, существующие
   таблицы не трогает).
2. **Проверить `.env`:** новые переменные необязательны, дефолты рабочие. `CORRECT_CABINET_RESTORE`
   по умолчанию `true`.
3. **Дать ИТРХАБ знать про `mainUser`** — поле необязательное, старые сообщения обрабатываются
   как раньше.
4. **Порядок включения боевого режима не меняется:** сначала накопить снимки и убедиться по
   логам, что план верный, затем `CORRECT_CABINET_DRY_RUN=false`.
