# Уточнение кабинета

ИТРХаб отправляет событие `correct-cabinet`. В JSON-поле `payload` находятся `userId`, `reg`, ссылка на исходный кабинет `link` и список `questions`. Каждый вопрос содержит текст `question` и выбранные варианты `answers`. Этот формат поддерживается без изменений портала.

Воркер получает адрес каталога по `reg`, открывает служебную сессию и читает дерево от кабинета из ссылки. Он обходит внутренние ссылки с защитой от циклов, ограничением глубины и числа страниц. Блокировка каталога сериализует уточнение с другими операциями записи.

## Как определяются блоки и виджеты

Для запросов с полным списком `options` воркер ищет страницы, на которых представлены все варианты. Он сравнивает реальные заголовки в Кодексе, учитывает архив и приводит к одному виду пробелы, регистр и `ё`. Текст вопроса используется для диагностики. Необязательное поле `blocks` ограничивает поиск точными названиями страниц. Если варианты расположены внутри одного виджета, поле `linkWidget` задаёт его заголовок, а варианты сравниваются с названиями ссылок.

Старый запрос содержит только выбранные ответы. Для таких запросов правила по заголовку исходного кабинета и вопросу восстанавливают полный список вариантов. В `cabinet_questionnaire_legacy.json` зафиксированы существующие анкеты «Метролога», «Руководителя производства» и «Кабинета новичка». Варианты совпадают с заголовками Кодекса, за исключением явно указанных расхождений. Например, для «Вида продукции» длинные формулировки портала соответствуют коротким названиям ссылок внутри виджета. Ответ «да» в вопросе о картотеках оставляет соответствующие виджеты, ответ «нет» скрывает их. Для «Эколога» сохранён прежний формат справочника.

До первой записи воркер проверяет весь план. Выбор должен входить в полный список вариантов, каждый заголовок должен быть однозначным в пределах страницы, а вопросы не должны управлять одним виджетом одновременно. Если одинаковый набор вариантов есть в предусмотренных рекомендованной и внешней ветках, обновляются обе копии. При несовпадении плана воркер отправляет событие в `correct-cabinet-dlq`.

## Запись и архив

Изначально в кабинете видны все варианты. При уточнении воркер архивирует невыбранные виджеты или ссылки с исходной позицией и конфигурацией. Служебные и вручную добавленные элементы вне списка вариантов остаются на странице. Если пользователь позже явно отметит скрытый вариант, воркер восстановит его из архива. Чтобы вернуть все скрытые варианты, нужно явно отметить каждый из них и остальные варианты, которые должны остаться видимыми. Пункт «Выбрать всё» пропускает вопрос и оставляет текущее состояние кабинета и архива, даже если вместе с ним отмечены другие пункты этого вопроса.

Для записи используется `editConfig`, который принимает полную конфигурацию страницы. Кодекс возвращает отсутствующие поля как `null`, в том числе внутри настроек поиска и виджетов. Бэкенд убирает такие поля при формировании запроса и при сравнении результата. Перед вызовом он сохраняет в своей PostgreSQL переход с конфигурациями до и после изменения. Затем он заново читает страницу из Кодекса и подтверждает запись в архиве. Если ответ на запись потерялся, сверка состояния позволяет завершить подтверждение без повторной мутации. Повтор того же выбора после подтверждения не вызывает новую запись.

Уточнение может охватывать несколько страниц. Проверка плана проходит до первой записи, а подтверждение выполняется по страницам. Если во время записи каталог недоступен, часть страниц могла успеть обновиться. При повторе подтверждённые изменения сохраняются, а неподтверждённые требуют сверки.

## Завершение запроса

После подтверждения всех страниц воркер публикует `cabinet-corrected` в формате, который уже читает ИТРХаб. Сообщение содержит `event_id`, `event_type` и строку JSON `payload` с полями `userId`, `reg`, `oldLink` и `link`. Идентификатор ответа стабилен при повторной доставке одного запроса. Портал по своему действующему правилу снимает ожидание после этого события.

При ошибке воркер передаёт причину в очередь ошибок. Действующий портал завершает ожидание по успешному событию. Для ошибки штатного завершающего события у него нет. Режим проверки плана `CORRECT_CABINET_DRY_RUN` выполняет чтение и валидацию без записи и без события об успехе.
